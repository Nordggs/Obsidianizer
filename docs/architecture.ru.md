# Архитектура Obsidianizer

> **Русский** | [English](architecture.md)

Этот документ — архитектурный контракт Obsidianizer. Конвейер, показанный
ниже, — фиксированный скелет; типы файлов подключаются как процессоры.

## Конвейер

```
                    ┌─────────────┐
                    │   ИСТОЧНИК  │
                    │             │
                    │ MD TXT SVG  │
                    │ PY ...      │
                    └──────┬──────┘
                           │
                         SCAN
                           │
                           ▼
                     ┌───────────┐
                     │ REGISTRY  │
                     └─────┬─────┘
                           │
                      PROCESSOR
                           │
                           ▼
                        EXTRACT
                           │
                           ▼
                    AI ENRICHMENT
                           │
                           ▼
                          EMIT
                           │
                   ┌────────┴────────┐
                   ▼                 ▼
               Markdown           Ассеты
                   │                 │
                   └────────┬────────┘
                            ▼
                        OBSIDIAN
```

## Стадии

### 1. guard

Проверка безопасности пересечения путей, выполняется до всего остального:

- `source == target` → отказ
- `target` внутри `source` → отказ
- `source` внутри `target` → отказ

Реализовано в `guard.py`. При сбое процесс завершается с поясняющим
сообщением и ненулевым кодом выхода.

### 2. scan

Рекурсивный обход папки-источника. Файл — кандидат, если его расширение
зарегистрировано в реестре процессоров. Незарегистрированные файлы никогда не
трактуются как заметки.

### 3. extract

Реестр направляет в процессор, зарегистрированный для расширения файла.
Процессор:

- формирует плоский словарь метаданных (title, даты, статистика, ссылки, …);
- возвращает оригинальное тело как есть (сырое содержимое сохраняется);
- возвращает локальные ссылки на медиа (пути, используемые этим файлом).

### 4. enrich

- Собирает YAML-frontmatter (+ `source_hash` для инкрементальности).
- Собирает человекочитаемый блок «визитки».
- Вставляет оригинальное тело без изменений под визиткой.
- Опциональный шаг LLM: отправляет ограниченный срез содержимого в локальный
  экземпляр Ollama; разбирает `SUMMARY:` / `TAGS:`. При любом сбое деградирует
  до пустых значений.

### 5. emit

- Атомарно записывает каждую заметку (`*.tmp` → `os.replace()`).
- Копирует каждый привязанный медиафайл в соответствующее относительное
  расположение в папке результата (сначала резолвится относительно каталога
  заметки, затем относительно корня источника).
- Собирает текущий манифест (каждый файл, созданный Obsidianizer за этот
  запуск).

### 6. manifest + prune

- Читает СТАРЫЙ `.obsidianizer-manifest.json` до перезаписи чего-либо.
- Если `--prune`: удаляет только `OLD - CURRENT` — никогда чужие файлы.
- Записывает ТЕКУЩИЙ манифест последним, атомарно, только после полного
  успеха.

## Инкрементальность

Каждый выходной frontmatter несёт:

```yaml
source_hash: <sha1 сырого файла>
```

При повторном запуске результат, чей `source_hash` совпадает с текущим сырым
файлом, полностью пропускается (без вызова LLM и перезаписи). Изменённый
источник извлекается, обогащается и записывается заново.

## Инварианты файловой системы

- Дерево источника: никогда не пишется, никогда не удаляется.
- Дерево результата: запись только через атомарную замену; учёт своих файлов
  через манифест.
- Манифест: `.obsidianizer-manifest.json` живёт в корне результата; в git
  игнорируется.
- Относительные пути медиа в заметках остаются валидными, потому что результат
  зеркалит относительную структуру каталогов источника.

## Детерминизм

Результат для одинаковых входных данных одинаков: извлечение метаданных
основано на регулярных выражениях, LLM-вывод — единственный
недетерминированный ингредиент, и только когда он явно включён.

## Слой UI

Десктопный GUI — основной пользовательский интерфейс. Он является *только
фронтендом*: каждая операция проходит через то же ядро, что и CLI. GUI ничего
не знает о Markdown/типах файлов; он отображает контракт событий ниже.

```
                    ┌──────────────────────┐
                    │         UI           │
                    │  source / target     │
                    │  Ollama / model      │
                    │  options             │
                    │  progress / log      │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │         CLI          │
                    └──────────┬───────────┘
                               │
                               ▼
                    ┌──────────────────────┐
                    │    CORE PIPELINE     │
                    └──────────────────────┘
```

- CLI и UI — два взаимозаменяемых фронтенда к одному ядру.
- GUI — основной пользовательский интерфейс; CLI — интерфейс для
  автоматизации.
- Ядро ничего не знает об UI; UI ничего не знает о Markdown/типах файлов.
  Общение идёт через контракт событий ниже.

### Контракт событий (`events.py`)

`events.py` — единственный источник истины. Ядро эмитит события через
необязательный колбэк `on_event` у `pipeline.run`; слушатели (CLI, GUI)
отображают их как угодно.

```python
Event(type=EventType, path=..., index=..., total=..., message=...)
```

| Событие         | Смысл                                                 |
|-----------------|-------------------------------------------------------|
| `SCAN_STARTED`  | партия найдена; `path` = корень источника             |
| `FILE_STARTED`  | начинается обработка файла; прогресс `index`/`total`  |
| `LLM_STARTED`   | начался вызов LLM для текущего файла                  |
| `FILE_DONE`     | файл обработан успешно                                |
| `FILE_SKIPPED`  | пропущен: без изменений через `source_hash`           |
| `FILE_ERROR`    | ошибка файла; `message` = текст ошибки                |
| `FINISHED`      | партия завершена; `message` = итоговые счётчики       |

Одно и то же событие `Event` отображается по-разному в каждом фронтенде:

- GUI: `✓ Обработан 17 из 120`
- CLI: `[17/120] ✓ filename.md`

Будущие фронтенды только подписываются на эти события; ядро конвейера не
меняется.

### Семантика остановки

`pipeline.run` принимает необязательный `cancel_check: Callable[[], bool]`. Он
опрашивается **только между файлами** — никогда внутри файла и никогда во
время вызова LLM. Текущий файл всегда доводится до конца (запрос к Ollama
может занимать до 180 с); UI сообщает «Остановка… текущий файл будет
завершён» вместо обещания мгновенной остановки.

При отмене:

- `Report.cancelled` становится `True` (только на этом пути);
- владение уже записанными файлами сохраняется через манифест (записывается
  только если был создан хотя бы один файл);
- `--prune` пропускается, `_index.md` не публикуется (незаконченное
  сканирование не должно ничего удалять или оставлять неполный индекс);
- `FINISHED` всё равно эмитится ровно один раз, со сводкой «отменено…».

Фатальная ошибка уровня запуска (любое исключение вне обработчика одного
файла) заполняет `Report.critical_error` и оставляет `Report.cancelled` равным
`False`; `FINISHED` всё равно эмитится ровно один раз («критическая ошибка:
…»). На любом пути — обычное завершение, ошибки файлов, отмена, фатальная
ошибка — `FINISHED` приходит ровно один раз.
