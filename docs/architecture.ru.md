# Архитектура Obsidianizer

> **Русский** | [English](architecture.md)

Этот документ — архитектурный контракт **конвейера обработки чатов**
Obsidianizer (инструменты ②/③). Фиксированный скелет — двухэтапный конвейер
«импорт → AI»; типы файлов подключаются как процессоры.

Полная карта всего приложения (включая Folder Obsidianizer — инструмент ①,
GUI-мост, полный контракт событий и раскладку сборки/релиза) — в корневом
[ARCHITECTURE.ru.md](../ARCHITECTURE.ru.md).

## Конвейер

Два фиксированных этапа с физически раздельными результатами:

```
            ┌─────────────┐
            │   ИСТОЧНИК  │  raw/ — архив только для чтения
            └──────┬──────┘
                   │  ЭТАП 1: импорт (без LLM)
                   ▼
            ┌─────────────┐
            │  PROCESSED  │  импорт + метаданные + медиа
            └──────┬──────┘
                   │  ЭТАП 2: AI-постобработка
                   ▼
            ┌─────────────┐
            │  ENRICHED   │  + LLM-резюме/теги/тема/тип
            └──────┬──────┘
                   ▼
           ХРАНИЛИЩЕ Obsidian  (указывает на enriched/)
```

Этап 1 (импорт без LLM):

```
                     ┌─────────────┐
                      │   ИСТОЧНИК  │
                      │  .md-файлы  │
                      │ (+плагины)  │
                     └──────┬──────┘
                            │
                          SCAN
                            │
                            ▼
                      ┌───────────┐
                      │ REGISTRY  │
                      └─────┬─────┘
                            │
                       PROCESSOR
                            │
                            ▼
                        EXTRACT
                            │
                            ▼
                          EMIT
                            │
                   ┌────────┴────────┐
                   ▼                 ▼
               Markdown           Ассеты
                   │                 │
                   └────────┬────────┘
                            ▼
                       PROCESSED
                            │   ЭТАП 2: postprocess.enrich
                            ▼
                       ENRICHED  ←  OBSIDIAN
```

Этап 2 (`postprocess.enrich`) читает каждую заметку в `processed/` и пишет
обогащённую копию в `enriched/`. Этот этап никогда не пишет в `processed/`.

## Стадии

### 1. guard

Проверка безопасности пересечения путей, выполняется до всего остального,
для каждой пары соседних этапов:

- `первый == второй` → отказ
- `второй` внутри `первого` → отказ
- `первый` внутри `второго` → отказ

Применяется трижды на каждом запуске: `(source, target)`, `(target, enriched)`
и `(source, enriched)` (AI-этап никогда не должен иметь возможности писать в
raw). Реализовано в `guard.py`; при нарушении выводится поясняющее сообщение и
ненулевой код возврата (`main()` возвращает `1`). Подкоманда `folders`
(Folder Obsidianizer) намеренно пропускает guard — карточки пишутся в
сканируемую папку по дизайну.

### 2. scan

Рекурсивный обход папки-источника. Файл — кандидат, если его расширение
зарегистрировано в реестре процессоров. Незарегистрированные файлы никогда не
трактуются как заметки.

### 3. extract

Реестр направляет в процессор, зарегистрированный для расширения файла.
Процессор:

- формирует плоский словарь метаданных (title, даты, статистика, ссылки, …);
- возвращает оригинальное тело как есть (сырое содержимое сохраняется);
- возвращает локальные ссылки на медиа (пути, используемые этим файлом).

### 4. emit

- Атомарно записывает каждую заметку (`*.tmp` → `os.replace()`).
- Копирует каждый привязанный медиафайл в соответствующее относительное
  расположение в папке результата (сначала резолвится относительно каталога
  заметки, затем относительно корня источника).
- Собирает текущий манифест (каждый файл, созданный Obsidianizer за этот
  запуск).

### 5. manifest + prune

- Читает СТАРЫЙ `.obsidianizer-manifest.json` до перезаписи чего-либо.
- Если `--prune`: удаляет только `OLD - CURRENT` — никогда чужие файлы.
- Записывает ТЕКУЩИЙ манифест последним, атомарно, только после полного
  успеха.

### 6. AI-постобработка (`postprocess.enrich`)

Второй этап, полностью независимый от импорта. Вызывается явно
(`obsidianizer ai`, кнопка GUI «AI-постобработка») или автоматически сразу
после реального импорта при включённом LLM.

Сигнатура:

```python
enrich(source_root: Path, target_root: Path, llm: LLMClient, *,
       prune: bool = False, on_event=..., cancel_check=...) -> EnrichReport
```

Для каждой заметки:

1. Разделить обработанную заметку на frontmatter/тело; прочитать
   `source_hash`.
2. **Актуально?** Копия в enriched существует и
   `enriched.ai_hash == source_hash` → пропуск (без вызова LLM и перезаписи).
3. Иначе `llm.analyze(body)` → резюме + теги + тема + тип; атомарно записать
   обогащённую заметку с `ai_hash = source_hash`.
4. Скопировать локально-привязанные медиа в enriched в той же относительной
   структуре, чтобы ссылки на картинки оставались валидными в хранилище.

После цикла: очистка сирот (опционально) и пересборка `enriched/_index.md`.

Очистка сирот (`--prune-enriched`): удаляет заметки enriched с маркером
владения `ai_hash`, чьей пары больше нет в processed, а также медиа, на
которые ссылались только они. Чужие файлы хранилища и всё ещё используемые
медиа никогда не трогаются.

## Folder Obsidianizer (инструмент ①)

Параллельный независимый движок (`obsidianize.py`), не входящий в конвейер
чатов. Он read-only сканирует обычную папку и пишет GitHub-подобную карточку на
каждую папку, сохраняя все пользовательские данные в парном файле
`<папка>_заметки.md`. Карточка несёт только сервисный frontmatter и полностью
регенерируема; свежесть решает контентно-хэшовый отпечаток (`ok` / `stale` /
`missing` / `conflict`), а обработка каждой папки изолирована — одна плохая
заметка не срывает прогон (сбои попадают в `summary.failed` с traceback в
логе). AI-обзор папки (`review.py`) пишет `<папка>_обзор.md`, который карточка
встраивает.

Полный контракт «карточка/заметки», синхронизация комментариев и интеграция с
Templater — в корневом [ARCHITECTURE.ru.md](../ARCHITECTURE.ru.md).

## Инкрементальность

Frontmatter этапа 1 несёт:

```yaml
source_hash: <sha1 сырого файла>
```

При повторном запуске результат, чей `source_hash` совпадает с текущим сырым
файлом, полностью пропускается (без вызова LLM и перезаписи). Изменённый
источник извлекается и записывается заново.

Этап 2 добавляет:

```yaml
ai_hash: <source_hash проанализированной заметки processed>
```

Копия в enriched пропускается, когда `ai_hash == processed.source_hash`. Эта
двойная защита делает конвейер естественно инкрементальным:

- новые источники → импортируются → ещё не обогащены → идут через Ollama;
- неизменённые источники → копии в enriched остаются как есть (без
  перевызовов);
- изменённые источники → импорт перезаписывает processed (новый
  `source_hash`), следующий AI-запуск видит расхождение и переобогащает только
  эту заметку;
- удалённые источники → их сироты в enriched удаляются только при
  `--prune-enriched`.

Обычный повторный импорт не может уничтожить AI-результат: enriched живёт в
отдельной папке и хранит свой маркер до тех пор, пока AI-этап его не
восстановит.

## Инварианты файловой системы

- Дерево источника: никогда не пишется, никогда не удаляется.
- Дерево результата (processed): пишется только этапом 1 через атомарную
  замену; учёт своих файлов через манифест. Этапом 2 не модифицируется.
- Дерево enriched: пишется только этапом 2 (атомарная замена); маркер
  `ai_hash` — основа владения для `--prune-enriched`; здесь же
  пересобирается `_index.md`.
- Манифест: `.obsidianizer-manifest.json` живёт в корне processed; в git
  игнорируется.
- Относительные пути медиа в заметках остаются валидными, потому что обе
  выходные папки зеркалят относительную структуру каталогов источника.

## Детерминизм

Результат для одинаковых входных данных одинаков: извлечение метаданных
основано на регулярных выражениях, frontmatter парсится PyYAML (с терпимым
построчным fallback) и детерминированно сериализуется, LLM-вывод — единственный
недетерминированный ингредиент, и только когда он явно включён.

## Слой UI

Десктопный GUI — основной пользовательский интерфейс. Он является *только
фронтендом*: он вызывает те же функции ядра, что и CLI (а **не** запускает CLI
через shell). GUI ничего не знает о Markdown/типах файлов; он отображает
контракт событий ниже.

```
        ┌──────────────────────┐        ┌──────────────────────┐
        │         UI           │        │         CLI          │
        │  source / target     │        │  флаги argparse      │
        │  Ollama / model      │        │                      │
        │  progress / log      │        │                      │
        └──────────┬───────────┘        └──────────┬───────────┘
                   │  прямые вызовы ядра           │
                   └───────────────┬───────────────┘
                                   ▼
                        ┌──────────────────────┐
                        │       ЯДРО           │
                        └──────────────────────┘
```

- CLI и UI — два взаимозаменяемых фронтенда к одному ядру. GUI вызывает
  `pipeline.run`, `postprocess.enrich`, `update_cards`, `topics.*` и
  `review.*` напрямую в рабочем потоке.
- GUI — основной пользовательский интерфейс; CLI — интерфейс для
  автоматизации.
- Ядро ничего не знает об UI; UI ничего не знает о Markdown/типах файлов.
  Общение идёт через контракт событий ниже.

### Постоянные настройки

`config.yml` — единственный источник постоянного пользовательского состояния
для CLI и GUI. Расположение определяется `config._user_data_dir()`:
`%LOCALAPPDATA%\Obsidianizer` во frozen-сборке, корень репозитория при запуске
из исходников.

- **чтение** — `Settings.load()` при старте заполняет форму (пути, модель,
  переключатель Ollama, флаги prune / dry-run);
- **запись** — `Settings.save()` вызывается при каждом подтверждённом
  изменении (`set_paths`, `set_llm`, `set_flags`), перед запуском обработки и
  при закрытии окна. Запись *сливает* данные в существующий файл
  (вручную правившиеся ключи сохраняются) и атомарна (`.tmp` → `os.replace`).
  Флаги CLI по-прежнему имеют приоритет над файлом.

Каждая кнопка `Выбрать` открывает проводник в своём последнем каталоге
(источник → source, результат → target, AI-результат → enriched). Если
сохранённый путь больше не существует, вместо падения диалог открывается в
ближайшем существующем родительском каталоге.

### Выбор модели и редактор промптов

AI-слой открывается переключателем «AI-постобработка» (Ollama — деталь
реализации, а не отдельная концепция). При выключенном переключателе
настройки модели и промпта скрыты в невидимом блоке `#aiDetails`; при
включении они появляются вместе с серой подписью «Локальная модель через
Ollama». Кнопки отражают состояние: «ОБРАБОТАТЬ» показывает «Импорт + AI»
или «Только импорт», а вторичная кнопка AI — «Только повторный AI-прогон»:

- **Модель**: комбо-бокс со свободным вводом и выпадающим списком
  установленных моделей (свой список, а не `datalist` — поэтому каждая
  установленная модель видна независимо от текущего текста в поле). Список
  запрашивается у Ollama по требованию (`list_models` → `GET /api/tags`) —
  только имена, содержимое чатов не отправляется. Текущая модель всегда
  остаётся в списке, поэтому переживает и перезапуск, и временно недоступную
  Ollama (показывается «Ollama недоступен», а не падение UI).
- **Промпты**: кнопка `Изменить…` открывает модальный редактор с четырьмя
  вкладками (импорт `prompt`, AI `ai_prompt`, тема `topic_prompt` и карта
  `map_prompt`).
  `get_prompts` возвращает шаблоны и их встроенные дефолты; `set_prompt`
  сохраняет отредактированный шаблон через `Settings.save()`; `reset_prompt`
  возвращает промпт к `DEFAULT_PROMPT` / `DEFAULT_AI_PROMPT` /
  `DEFAULT_TOPIC_PROMPT` / `DEFAULT_TOPIC_MAP_PROMPT` — сами встроенные дефолты
  никогда не перезаписываются, а `{content}` остаётся единственной точкой
  подстановки текста файла/чата.

### Объединение в тему (`topics.py`)

Строитель тем сливает несколько чатов в одну заметку-знание — слой второго
уровня, который ссылается на источники вместо их копирования:

    processed/ (выбранные чаты) → один вызов LLM → enriched/topics/<Имя>.md

- **Выбор**: модалка GUI (`list_chats` → чекбоксы + поиск) передаёт
  относительные пути processed в `create_topic`. Принимаются только файлы с
  маркером владения `source_hash`.
- **Payload**: каждый чат становится блоком `## Файл` (название/источник/дата +
  фрагмент тела). Бюджет символов (`TOPIC_LIMIT_CHARS`, 16k) распределяется
  равномерно, поэтому представлен каждый чат; большой выбор вырождается в
  короткие фрагменты, но никогда — в непомерный запрос.
- **Контракт**: один вызов LLM возвращает NAME / SUMMARY / DECISIONS /
  KEY_FACTS / ARTIFACTS (`parse_topic_response`, деградация к пустым полям
  при сбое). Имя файла берётся из блока NAME модели (`sanitize_name`), так
  что пользователь не вводит имя темы вручную.
- **Результат**: `enriched/topics/<Имя>.md` с `topic_hash` и `chats` в
  frontmatter, карточкой знаний (Суть / Решения / Ключевые факты /
  Артефакты) и `[[wiki]]`-ссылками на чаты по сервисам. `_index.md`
  пересобирается, поэтому тема появляется в навигации.
- **Инкрементальность**: `topic_hash` = sha1 от отсортированных `source_hash`
  выбранных чатов. Существующая тема с тем же хэшем пропускает вызов LLM;
  изменившийся выбор запускает анализ заново и перезаписывает тему.

**Авто-группировка** (`topics.group_all`, кнопка «Авто-группировка») убирает
ручной выбор: вся коллекция processed кластеризуется LLM за один проход карты,
затем каждый кластер из двух и более чатов проходит тот же путь
`create_topic`:

- Вызов `map_prompt` получает карточки чатов (`[idx] название (сервис, дата)`
  плюс короткий фрагмент тела); ответ — повторяющиеся блоки `TOPIC:` / `IDS:`
  (`parse_topic_map`). Индексы — 1-индексированные *глобальные* индексы
  коллекции; чат принадлежит только первой подходящей теме.
- Большие коллекции разбиваются на чанки по размеру payload
  (`MAP_CHUNK_CHARS`); уже найденные имена тем передаются в следующий чанк,
  чтобы одна тема сохраняла имя.
- Кластеры из одного чата считаются и пропускаются (`one_chat`); существующие
  темы никогда не удаляются — изменившаяся кластеризация только добавляет/
  обновляет темы.
- GUI запускает проход через `group_all()`; `TOPIC_MAP_STARTED` открывает
  проход карты, затем по одному `TOPIC_FILE_*` на создаваемую тему.

Пофайловый AI-проход остаётся доступен как явное действие
«AI-постобработка», но «ОБРАБОТАТЬ» больше не запускает AI автоматически —
импорт и AI это отдельные осознанные шаги.

### Контракт событий (`events.py`)

`events.py` — единственный источник истины. Ядро эмитит события через
необязательный колбэк `on_event`; слушатели (CLI, GUI) отображают их как
угодно. Ниже перечислены все `EventType` — `message` это локализованный текст
для показа, `data` — машиночитаемый payload.

```python
Event(type=EventType, path=..., index=..., total=..., message=..., data=...)
```

| Семейство | Событие | Смысл |
|-----------|---------|-------|
| Партия (этап 1) | `SCAN_STARTED` | партия найдена; `path` = корень источника |
| | `FILE_STARTED` | начинается обработка файла; прогресс `index`/`total` |
| | `LLM_STARTED` | начался опциональный вызов LLM на файл |
| | `FILE_DONE` | файл обработан успешно |
| | `FILE_SKIPPED` | пропущен: без изменений через `source_hash` |
| | `FILE_ERROR` | ошибка файла; `message` = текст ошибки |
| | `FINISHED` | партия завершена; `message` = итоговые счётчики |
| AI-enrich (этап 2) | `AI_SCAN_STARTED` | этап 2 обнаружил партию processed |
| | `AI_FILE_STARTED` | AI-проход по заметке processed |
| | `AI_FILE_DONE` | обогащённая заметка записана |
| | `AI_FILE_SKIPPED` | копия в enriched уже актуальна |
| | `AI_FILE_ERROR` | ошибка заметки на этапе 2 |
| | `AI_FINISHED` | этап 2 завершён; `message` = счётчики AI |
| Сборка тем | `TOPIC_SCAN_STARTED` | запущен прогон тем |
| | `TOPIC_MAP_STARTED` | начался проход кластеризации (авто-группировка) |
| | `TOPIC_FILE_STARTED` | строится тема |
| | `TOPIC_FILE_DONE` | заметка темы записана |
| | `TOPIC_FILE_ERROR` | ошибка темы |
| | `TOPIC_FINISHED` | прогон тем завершён |
| Жизненный цикл тем | `TOPIC_UPDATED` / `TOPIC_RENAMED` / `TOPIC_DELETED` | результат управления темой |
| AI-чат | `CHAT_REPLY` / `CHAT_ERROR` | интерактивный ответ / сбой |
| | `CHAT_FOUND` | поиск нашёл чаты-кандидаты под вопрос |
| Folder Obsidianizer | `OBS_SCAN_STARTED` | дерево папок найдено |
| | `OBS_FOLDER_DONE` | папка обработана; `message` = действие |
| | `OBS_FINISHED` | прогон завершён; `data` = счётчики, включая `failed` |
| | `OBS_ERROR` | сбой уровня прогона |
| Обзор папки | `REVIEW_STARTED` | запущен прогон обзора |
| | `REVIEW_FOLDER_DONE` | записан `<папка>_обзор.md` |
| | `REVIEW_FINISHED` | прогон обзора завершён |
| | `REVIEW_ERROR` | сбой прогона обзора |

Одно и то же событие `Event` отображается по-разному в каждом фронтенде:

- GUI: `✓ Обработан 17 из 120`
- CLI: `[17/120] ✓ filename.md`

Будущие фронтенды только подписываются на эти события; ядро конвейера не
меняется.

### Семантика остановки

`pipeline.run` принимает необязательный `cancel_check: Callable[[], bool]`. Он
опрашивается **только между файлами** — никогда внутри файла и никогда во
время вызова LLM. Текущий файл всегда доводится до конца (запрос к Ollama
может занимать до 180 с); UI сообщает «Остановка… текущий файл будет
завершён» вместо обещания мгновенной остановки.

При отмене:

- `Report.cancelled` становится `True` (только на этом пути);
- владение уже записанными файлами сохраняется через манифест (записывается
  только если был создан хотя бы один файл);
- `--prune` пропускается, `_index.md` не публикуется (незаконченное
  сканирование не должно ничего удалять или оставлять неполный индекс);
- `FINISHED` всё равно эмитится ровно один раз, со сводкой «отменено…».

Фатальная ошибка уровня запуска (любое исключение вне обработчика одного
файла) заполняет `Report.critical_error` и оставляет `Report.cancelled` равным
`False`; `FINISHED` всё равно эмитится ровно один раз («критическая ошибка:
…»). На любом пути — обычное завершение, ошибки файлов, отмена, фатальная
ошибка — `FINISHED` приходит ровно один раз.
